## 2. Architecture Before T01
- Bunker fuel scraper and FX scraper pulled data and only wrote the current value to Redis with a 24-hour TTL. No history was maintained.
- Freight rates were written to PostgreSQL via `on_conflict_do_update` using `rate_date`, successfully accumulating history.

## 3. Architecture After T01
- **Bunker Persistence:** `BunkerScraper` writes to Redis (preserving existing cache behavior) and then performs an idempotent `insert(...).on_conflict_do_update()` into the `bunker_rates` PostgreSQL table.
- **FX Persistence:** `ExchangeRateScraper` writes to Redis (preserving existing behavior) and performs an idempotent upsert into the `exchange_rates` PostgreSQL table.
- **Freight Rates & Carrier Advisories:** Left unchanged as they already accumulate history safely.

## 5. Bunker Persistence Design
- The upstream source (`shipandbunker.com`) provides current daily prices.
- The scraper loop extracts prices for each tracked port.
- Before committing to PostgreSQL, the scraper wraps the query in a try-except block so that if the database is down, it fails gracefully without breaking the Redis update or the entire task.

## 6. FX Persistence Design
- Upstream source (`exchangerate-api.com`) provides latest daily conversion rates.
- The base currency is fixed to `USD` and quote to `EGP`.
- Persistence uses `on_conflict_do_update` grouped by currency pair and date to ensure daily idempotency.
- Any DB failure is caught and logged, falling through gracefully since Redis was already updated.

## 7. Timestamp Semantics
- `observed_date`: The logical date of the market observation. Since neither source provides a precise historical timestamp in their scraped payload, `datetime.now(timezone.utc).date()` is used at the time of scraping.
- `created_at`: The exact database insertion timestamp (auto-generated by PostgreSQL).

## 8. Idempotency Strategy
- **Bunker:** Uniqueness constraint on `(port_name, fuel_type, observed_date)`. If the scraper runs multiple times a day, the `price_usd` is updated for that day.
- **FX:** Uniqueness constraint on `(base_currency, quote_currency, observed_date)`. If retried on the same day, `exchange_rate` is updated.
- Both use PostgreSQL's native `ON CONFLICT DO UPDATE` ensuring atomic, race-condition-free idempotency.
